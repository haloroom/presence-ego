# AI가 읽기 쉬운 풀스택 — 시리즈 설계 문서

> AI 코딩 시대, 아키텍처를 어떻게 구성해야 AI 에이전트가 코드베이스를 더 잘 이해하고 정확한 코드를 생성하는가?

---

## 시리즈 개요

### 관통 질문

**"AI 에이전트가 코드베이스를 더 잘 이해하고, 더 정확한 코드를 생성하려면 어떤 구조와 기술이 유리한가?"**

단순한 기술 비교가 아니라, **AI 인지 친화성(AI Cognizability)**이라는 렌즈로 풀스택 아키텍처의 각 계층을 평가한다.

### 독자

이미 풀스택 경험이 있고, AI 코딩 시대에 아키텍처를 어떻게 재구성할지 고민하는 시니어 개발자

### 카테고리 / 형식

- 카테고리: `study` (리서치 기반 객관적 기술 정리)
- 형식: `web-tech-landscape.md` 스타일 — 비교 테이블, 코드 예시, 구조 다이어그램
- 3편 시리즈

## 1편: DB와 백엔드 — AI가 잘 읽는 데이터 계층

### 도입

- "바이브 코딩(Vibe Coding)"의 등장 배경 — Andrej Karpathy (2025)
- AI 코딩이 단순 코드 생성을 넘어 **아키텍처 선택**에까지 영향을 미치는 현상
- 시리즈의 관통 질문 제시

### 1. 데이터베이스 — AI 학습 데이터와의 친화성

#### 핵심 논점
- AI 모델의 학습 데이터에서 SQL이 차지하는 비중이 압도적 → **표준 SQL 기반 DB**에서 AI가 더 정확한 쿼리를 생성
- 독자 SDK 기반(Firebase Firestore) → AI가 독자적 메서드 체인 학습 데이터에 의존해야 하므로 오류 가능성 상승

#### 비교 대상

| DB | 엔진 | AI 강점 | 가격 모델 | 적합 케이스 |
|:---|:---|:---|:---|:---|
| **Supabase** | PostgreSQL | pgvector(벡터 검색), 표준 SQL, RLS 정책 | 사용량 기반 + 무료 티어 | 데이터 중심 SaaS, RAG 앱 |
| **Neon** | PostgreSQL (서버리스) | 즉시 브랜칭(Git for DB), scale-to-zero | 사용량 기반 + 무료 티어 | 모듈형 스택, AI 실험 |
| **Firebase** | Firestore (NoSQL) | Google Cloud AI 통합, 실시간 동기화 | 읽기/쓰기 기반 | 모바일 퍼스트, 실시간 앱 |
| **Turso** | libSQL (SQLite 포크) | 엣지 내장, AI 에이전트별 격리 DB | 행/저장 기반 | 읽기 중심, 엣지 퍼스트 |
| **PlanetScale** | MySQL (Vitess) + PostgreSQL | 브랜치 기반 스키마 마이그레이션 | 프로비저닝 기반 (유료 전용) | 고처리량 관계형 데이터 |

#### 리서치 근거
- Supabase: 표준 SQL이므로 AI 코딩 어시스턴트(Cursor, Claude Code)가 복잡한 쿼리, 마이그레이션, RLS 정책을 정확하게 생성
- Neon: 즉시 브랜칭으로 프로덕션 DB 전체를 복제해 AI 실험(프롬프트 테스트, 벡터 검색 알고리즘) 가능
- Turso: Rust 기반 "Project Limbo" 엔진이 네이티브 벡터 검색과 동시 쓰기 지원, AI 에이전트 인프라에 특화

### 2. ORM — 스키마가 곧 계약

#### 핵심 논점
- ORM의 스키마 정의가 AI에게 "이 프로젝트의 데이터 구조는 이것이다"라는 계약 역할
- 코드젠 의존 여부, 번들 사이즈, 엣지 호환성이 AI 코딩 환경에서의 실질적 차이

#### 비교 대상

| 특성 | Prisma | Drizzle ORM |
|:---|:---|:---|
| **철학** | Schema-first (`.prisma` DSL) | SQL-first (TypeScript as SQL wrapper) |
| **타입 안전** | 생성된 클라이언트 (`prisma generate`) | 코드에서 직접 추론 (코드젠 없음) |
| **번들 사이즈** | ~1.6MB (TypeScript/WASM) | ~7.4KB (제로 런타임 의존) |
| **AI 코딩 관점** | 선언적 `.prisma` 파일 → AI가 전체 데이터 모델을 한눈에 파악 | TypeScript 스키마 → 코드젠 스텝 없이 타입 즉시 전파 |
| **적합 환경** | 팀 프로젝트, SQL 추상화 선호 | 엣지/서버리스, SQL 직접 제어 선호 |

#### Zod 연계 — 단일 스키마 흐름
- Zod로 스키마를 한 번 정의 → TypeScript 타입 추론 → API 응답 검증 → 프론트엔드 폼 검증
- DB 스키마 → ORM 타입 → API 계약 → 프론트엔드 타입: **하나의 소스에서 전체 스택의 타입이 파생**
- AI가 이 "계약"을 읽으면 전체 데이터 흐름을 이해 → 계층 간 불일치 오류 감소

### 3. 백엔드 아키텍처 — 서버리스 / BaaS / 전통 서버

#### 핵심 논점
- AI가 가장 정확한 코드를 생성하는 백엔드 패턴은 무엇인가?
- 선언적 API(BaaS) vs 명령적 API(Express) — AI 코드 생성 정확도의 차이

#### 비교 대상

| 아키텍처 | 대표 기술 | AI 코딩 관점 강점 | 약점 |
|:---|:---|:---|:---|
| **서버리스 (FaaS)** | Vercel Functions, Cloudflare Workers | 단일 함수 패턴 → AI가 범위를 좁혀 정확한 코드 생성 | 콜드 스타트, 상태 관리 한계 |
| **BaaS** | Supabase, Convex | 선언적 API → AI가 "무엇을 할지"만 기술하면 됨 | 벤더 종속, 복잡한 비즈니스 로직 한계 |
| **전통 서버** | Express, FastAPI, Hono | 학습 데이터 풍부 → 복잡한 패턴도 AI가 잘 생성 | 운영 복잡도, 스케일링 직접 관리 |

#### BaaS 심화 — Supabase vs Convex

| 특성 | Supabase | Convex |
|:---|:---|:---|
| **기반** | PostgreSQL (관계형) | Reactive Document Store |
| **실시간** | 옵트인 구독 | 기본 내장 (자동 반응형) |
| **언어** | SQL + 생성된 타입 | TypeScript 네이티브 (엔드투엔드) |
| **AI 강점** | pgvector 기반 SQL RAG | 실시간 AI UI/스트리밍에 최적 |
| **적합 케이스** | 관계형 데이터, 자체 호스팅 필요 시 | 실시간 협업 도구, AI 채팅 앱 |

#### 하이브리드 전략
- **핫 패스**(인증, 데이터 조회) → BaaS/서버리스로 처리
- **무거운 처리**(영상 생성, 대규모 문서 파싱) → Railway, AWS ECS 등 컨테이너 오프로드
- AI 코딩 관점: 핫 패스는 선언적 패턴으로, 무거운 처리는 명령적 패턴으로 분리하면 AI가 각 영역에서 최적 코드 생성

## 2편: 프론트엔드와 배포 — AI가 예측 가능한 패턴

### 1. 프레임워크 선택 — 컨벤션이 곧 컨텍스트

#### 핵심 논점
- **컨벤션 기반 프레임워크**는 디렉토리 구조 → 라우팅, 파일명 → 역할이라는 예측 가능한 매핑을 제공
- AI는 이 매핑을 학습했으므로, 컨벤션이 강한 프레임워크에서 더 정확한 코드를 생성

#### 비교 대상
- **Next.js App Router**: 파일 기반 라우팅 (`app/about/page.tsx` → `/about`)의 예측 가능성
  - AI가 "about 페이지 만들어"라는 요청을 받으면 파일 위치를 즉시 결정 가능
  - Server Components / Client Components 경계가 명시적 → AI가 렌더링 전략을 올바르게 선택
- **Astro**: 콘텐츠 퍼스트 + 멀티 프레임워크 지원
  - Content Collections로 콘텐츠 구조가 스키마로 정의됨 → AI가 데이터 구조를 정확히 파악
  - Islands 아키텍처: 어디에 JS가 필요한지 명시적 → AI가 불필요한 클라이언트 JS 생성 방지
- **SvelteKit**: 컴파일러 접근
  - 런타임 프레임워크 부재 → AI 생성 코드의 번들 오버헤드 최소화
  - 직관적인 반응성 문법 → AI가 상태 관리 코드를 더 간결하게 생성

#### AI 스캐폴딩 도구
- **v0.dev** (Vercel): React/Next.js 컴포넌트 생성 → Vercel 생태계와 자연스러운 연결
- **Lovable**, **Bolt.new**: 전체 앱 스캐폴딩 → 대부분 React/Next.js 기반으로 생성

### 2. 배포 플랫폼 — "제로 컨피그"와 AI 생성 코드의 적합성

#### 비교 테이블

| 특성 | Vercel | Cloudflare Pages | Netlify |
|:---|:---|:---|:---|
| **최적 대상** | Next.js 풀스택 앱 | 글로벌 엣지 성능 + 비용 효율 | 정적 사이트, JAMstack |
| **엣지 네트워크** | 글로벌 (Next.js 최적화) | 330+ 로케이션 (최대 규모) | CDN 기반 |
| **가격 모델** | 사용량 기반 (급증 가능) | 대역폭 무료 (예측 가능) | 크레딧 기반 (균형) |
| **AI 코딩 시너지** | v0.dev 생성 코드의 기본 배포지 | Workers 생태계 (학습 곡선 있음) | 프레임워크 중립 (Astro/Hugo) |
| **프리뷰 배포** | ✅ Git 커밋별 자동 생성 | ✅ 지원 | ✅ 지원 |

#### AI 코딩 관점 판단 기준
- **AI 생성 코드의 배포 마찰**: Vercel은 "Git push = 배포" 수준의 제로 컨피그 → AI가 생성한 코드를 가장 빠르게 검증
- **프리뷰 배포**: AI가 생성한 UI 변경을 프로덕션 전에 시각적으로 검증하는 핵심 메커니즘
- **비용 예측성**: AI 코딩으로 잦은 배포가 발생 → Cloudflare의 대역폭 무료 모델이 비용 관점에서 유리

### 3. 모노레포 — AI의 단일 컨텍스트

#### 핵심 논점
- AI 에이전트는 컨텍스트 윈도우 내의 정보로 판단 → **모노레포**는 전체 프로젝트를 하나의 컨텍스트로 제공
- 멀티레포에서는 AI가 다른 레포의 인터페이스를 "추측"해야 함 → 오류 증가

#### 표준 구조

```
my-monorepo/
├── apps/
│   ├── web/               # Frontend (Next.js, Vite)
│   └── api/               # Backend (Hono, Express)
├── packages/
│   ├── ui/                # 공유 UI 컴포넌트
│   ├── types/             # 공유 TypeScript 타입
│   ├── database/          # ORM 스키마 & 클라이언트
│   └── config/            # 공유 설정 (tsconfig, eslint)
├── docs/                  # 아키텍처, 스펙 문서
├── AGENTS.md              # AI 에이전트 컨텍스트
├── pnpm-workspace.yaml
├── turbo.json
└── package.json
```

#### AI에게 시맨틱을 주는 디렉토리 구조
- `packages/database/` → "여기에 데이터 모델이 있다"
- `packages/types/` → "프론트와 백이 공유하는 계약이 여기에 있다"
- `apps/web/` → "사용자가 보는 인터페이스"
- 디렉토리 이름 자체가 AI에게 주는 **시맨틱 메타데이터**

#### 도구 선택
- **Turborepo**: 빌드 캐싱 + 병렬 실행, Vercel 리모트 캐시 지원
- **pnpm**: 엄격한 의존성 트리로 "팬텀 디펜던시" 방지 → AI가 실제 존재하는 패키지만 import

## 3편: 설계 원칙과 보안 — AI와 협업하는 코드베이스

### 1. 컨텍스트 엔지니어링 — AI에게 "의도"를 전달하는 구조

#### AGENTS.md — "기계를 위한 README"
- 사람을 위한 `README.md` vs AI를 위한 `AGENTS.md`
- 30+ 도구가 네이티브 지원 (Claude Code, GitHub Copilot, Cursor, Aider, Windsurf)
- 200줄 이하 권장: 토큰 비용 + 인퍼런스 품질의 균형
- 포함 항목: 빌드/테스트 커맨드, 코딩 표준, 경계(하지 말아야 할 것), 기술 스택

#### Progressive Disclosure — 계층적 문서 구조
- 루트 `AGENTS.md`: 프로젝트 전체 디폴트
- 서브 디렉토리 오버라이드: `services/payments/AGENTS.md` → 결제 모듈 전용 규칙
- `docs/` 링크: 깊은 아키텍처 스펙은 참조만 → AI가 필요 시에만 탐색

#### MCP (Model Context Protocol) — AI의 외부 도구 접근 표준
- AI 에이전트가 DB, API, 브라우저, 파일 시스템 등 외부 도구에 접근하는 표준 인터페이스
- 플러그인 기반 확장: Chrome DevTools, Firebase, Science DB 등
- AI가 "코드를 쓰는 것"을 넘어 "도구를 사용하는 것"으로 역할 확장
- 프로젝트별 `mcp_config.json`으로 사용 가능한 도구 범위를 명시적으로 제한

#### 스킬(Skills) — 재사용 가능한 지식 캡슐화
- 복잡한 워크플로우를 SKILL.md + 스크립트 + 예시로 패키징
- AI가 처음 보는 작업이어도 스킬 파일을 읽으면 즉시 수행 가능
- 예: "디버깅 스킬" → 4단계 프레임워크(원인 조사 → 패턴 분석 → 가설 검증 → 구현)
- 프로젝트별 커스텀 스킬 + 글로벌 공유 스킬의 계층 구조

#### 서브 에이전트(Sub-agents) — 에이전트 분업 패턴
- 독립적인 작업을 여러 AI 에이전트에게 병렬로 위임
- read-only 리서치 에이전트, write 권한을 가진 구현 에이전트 등 역할 분리
- 메인 에이전트가 오케스트레이터 역할 → 복잡한 프로젝트도 체계적 진행
- 격리된 워크스페이스(branched workspace)에서 안전한 병렬 실행

#### Plan → Act → Reflect 패턴
- AI 에이전트에게 실행 전 `plan.md` 작성을 강제하는 구조
- 계획 → 실행 → 검증의 루프가 AI 코드 품질을 구조적으로 보장
- "한 번에 큰 기능 생성" 대신 "작은 단위의 반복 실행"

### 2. 타입 시스템과 스키마 — AI 오류를 구조적으로 줄이는 방법

#### TypeScript strict mode의 효과
- `strict: true` → AI가 생성한 코드에서 `any` 사용 방지, 누락된 null 체크 감지
- 타입 에러가 즉시 피드백 → AI가 "스스로 수정"할 수 있는 루프 형성
- AI에게 "이 코드는 타입 에러가 나면 안 된다"는 구조적 제약 부여

#### 계약-우선 개발 (Contract-First)
- **oRPC / tRPC**: 프론트-백 API 계약을 TypeScript로 공유
- **OpenAPI / Protobuf**: 폴리글랏 환경에서 언어 간 타입 동기화
- AI가 API를 수정하면 자동으로 프론트엔드 타입도 업데이트 → **타입 드리프트 방지**

#### 단일 스키마 흐름
```
Zod Schema → Drizzle Table → API Response Type → Frontend Form Validation
     │              │               │                    │
     └──── 하나의 소스에서 전체 스택의 타입이 파생 ────┘
```
- AI가 스키마 하나만 읽으면 전체 데이터 흐름을 이해
- 계층 간 불일치가 구조적으로 불가능

### 3. 보안 가드레일 — AI 생성 코드의 신뢰 경계

#### AI 생성 코드의 보안 현실
- 연구에 따르면 **~45%**의 AI 생성 코드가 보안 취약점 포함
- AI는 "동작하는 코드"에 최적화, "안전한 코드"에는 최적화되지 않음
- 주요 취약점: SQL Injection, XSS, 안전하지 않은 인증, 커맨드 인젝션

#### "Verify Before Merge" 원칙
- AI 생성 코드를 **신뢰하지 않는 입력**으로 취급
- 인증, 인가, 결제, 민감 데이터 처리 → **시니어 엔지니어의 필수 수동 리뷰**
- CI/CD 파이프라인에 SAST/SCA 도구 통합 → 자동 취약점 차단

#### 구체적 보안 프롬프팅
- ❌ "로그인 기능 추가해줘"
- ✅ "bcrypt로 해싱, 파라미터화된 쿼리로 DB 접근, 강력한 시크릿 관리 전략의 JWT 인증을 생성해줘"
- 입력 검증, 레이트 리미팅, 에러 핸들링을 **모든 프롬프트에 명시**

#### Dependency Hallucination(슬롭스쿼팅) 방어
- AI가 존재하지 않는 라이브러리를 추천 → 공격자가 해당 이름으로 악성 패키지 등록
- 방어: AI 추천 의존성을 알려진 레지스트리와 교차 검증
- `pnpm`의 엄격한 의존성 관리가 추가 방어선

#### 환경 변수 격리와 크리덴셜 관리
- AI 에이전트에게 프로덕션 크리덴셜 접근 차단
- 환경 변수 템플릿(`.env.example`)만 노출
- 시크릿은 Vault / Secret Manager로 격리

### 4. 마무리 — AI 시대 개발자의 역할 변화

- "수위가 올라갔다: 모든 사람이 코드를 배포할 수 있지만, 건강한 시스템을 배포할 수 있는 사람은 적다"
- 코드 작성자 → **시스템 설계자 + AI 오케스트레이터**로의 전환
- AI가 "삽질"(보일러플레이트, 루틴 리팩토링)을 제거 → 개발자는 복잡한 비즈니스 문제와 시스템 신뢰성에 집중
- **아키텍처적 판단, 보안, 성능, 컨텍스트 관리**가 AI 시대의 핵심 역량
