시리즈의 지난 글에서는 AI 에이전트가 코드를 예측하고 작성하기 쉬운 기술 스택과 아키텍처에 대해 다루었습니다. 1편에서는 표준 SQL과 스키마-퍼스트 ORM이 AI에게 유리한 이유를, 2편에서는 컨벤션 기반 프레임워크와 모노레포가 제공하는 높은 예측 가능성에 대해 논의했습니다.

이번 3편의 초점은 단순한 기술 선택을 넘어 **"AI와 협업하는 구조"** 그 자체에 있습니다. 사람이 이해하기 쉬운 코드가 반드시 AI가 이해하기 쉬운 코드는 아닙니다. AI 에이전트가 코드베이스를 컨텍스트로 받아들이고, 도구를 사용하며, 안전하게 코드를 생성할 수 있도록 돕는 설계 원칙, 도구 생태계, 그리고 보안 가드레일에 대해 정리합니다.

---

## 1. 컨텍스트 엔지니어링 — AI에게 "의도"를 전달하는 구조

**컨텍스트 엔지니어링**은 AI 에이전트가 프로젝트의 규칙, 목표, 컨벤션을 오해 없이 파악할 수 있도록 코드베이스 주변의 정보를 구조화하는 작업입니다.

### AGENTS.md — "기계를 위한 README"

`README.md`가 사람을 위한 프로젝트 개요라면, `AGENTS.md`는 기계를 위한 지침서입니다. Claude Code, GitHub Copilot, Cursor, Windsurf, Antigravity 등 30개 이상의 AI 도구들이 이 파일을 네이티브로 지원하며 시스템 프롬프트의 일부로 활용합니다.

토큰 비용과 인퍼런스 품질의 균형을 위해 보통 **200줄 이하**로 간결하게 작성하는 것이 권장됩니다. 이 파일에는 빌드/테스트 커맨드, 코딩 표준, 하지 말아야 할 경계(Boundaries), 기술 스택이 포함되어야 합니다.

```markdown
# AI Agent Guidelines

## Tech Stack
- Frontend: Next.js (App Router), Tailwind CSS
- Backend: Node.js, Drizzle ORM, PostgreSQL

## Rules
- <strong>DO NOT</strong> use `any` in TypeScript. Always define proper types.
- All new components must be placed in `src/components/ui/`.
- Run `npm run test` before finalizing any logic changes.
```

### Progressive Disclosure — 계층적 문서 구조

모든 지침을 하나의 루트 `AGENTS.md`에 몰아넣으면 컨텍스트 윈도우가 낭비되고 AI가 핵심을 놓칠 수 있습니다. 이를 해결하기 위해 <strong>Progressive Disclosure(점진적 공개)</strong> 패턴을 사용합니다.

- **루트 `AGENTS.md`**: 프로젝트 전체의 디폴트 규칙
- **서브 디렉토리 오버라이드**: 특정 도메인에 진입할 때만 읽히는 규칙 (예: `services/payments/AGENTS.md`)
- **`docs/` 링크**: AI가 세부 구현 방식이 필요할 때 능동적으로 탐색할 수 있도록 파일 경로만 제공

### MCP(Model Context Protocol) — AI의 외부 도구 접근 표준

<strong>MCP(Model Context Protocol)</strong>는 AI 에이전트가 데이터베이스, 외부 API, 브라우저, 파일 시스템 등 외부 도구에 접근할 수 있도록 돕는 표준 인터페이스입니다. 

기존에는 AI가 "코드를 써주는 역할"에 머물렀다면, MCP를 통해 AI는 "도구를 직접 사용하여 문제를 해결하는 역할"로 확장됩니다. 프로젝트 최상단의 `mcp_config.json`을 통해 AI가 접근할 수 있는 도구와 권한의 범위를 명시적으로 제한할 수 있습니다.

```json
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/mydb"]
    }
  }
}
```

### 스킬(Skills) — 재사용 가능한 지식 캡슐화

반복적이고 복잡한 워크플로우를 AI에게 매번 설명하는 것은 비효율적입니다. 이를 `SKILL.md` 문서와 스크립트로 패키징하여 지식을 캡슐화할 수 있습니다. AI가 처음 보는 도메인이나 작업이어도, 이 스킬 파일을 읽으면 즉시 업무를 수행할 수 있게 됩니다.

```markdown
# 디버깅 워크플로우 스킬 (SKILL.md)

1. 서버 로그와 에러 트레이스를 수집한다.
2. 에러가 발생한 파일과 관련 의존성을 파악한다.
3. `plan.md` 파일에 가설과 수정 계획을 작성한다.
4. 코드를 수정하고 단위 테스트를 실행하여 검증한다.
```

### 서브 에이전트(Sub-agents) — 에이전트 분업 패턴

복잡한 요구사항은 단일 에이전트에게 맡기기보다 <strong>서브 에이전트(Sub-agents)</strong> 패턴으로 분업하는 것이 유리합니다.
메인 에이전트(Orchestrator)가 계획을 수립하고, 읽기 전용 권한을 가진 리서치 에이전트가 코드를 분석하며, 쓰기 권한을 가진 구현 에이전트가 격리된 워크스페이스(Branched Workspace)에서 코드를 작성해 안전하게 병렬로 작업을 실행합니다.

### Plan → Act → Reflect 패턴

AI에게 코드를 바로 작성하게 하는 대신, 실행 전 `plan.md` 작성을 강제하는 구조를 도입해야 합니다. "한 번에 거대한 기능을 생성"하는 방식은 실패 확률이 높습니다. **계획 → 실행 → 검증**의 짧은 루프가 AI가 생산하는 코드의 품질을 구조적으로 보장합니다.

> **💡 핵심 요약**: AI는 무한한 타이핑 속도를 가졌지만, 방향을 잡아주는 명시적인 컨텍스트 경계가 없으면 쉽게 길을 잃습니다.

## 2. 타입 시스템과 스키마 — AI 오류를 구조적으로 줄이는 방법

AI가 생성한 코드의 논리적 오류를 잡아내는 가장 효과적인 방어선은 강력한 타입 시스템입니다.

### TypeScript strict mode의 효과

프로젝트 설정에서 `strict: true`를 강제하면 AI가 무분별하게 `any`를 남발하는 것을 막고, null 체크 누락을 컴파일 타임에 감지할 수 있습니다. AI 에이전트는 타입 에러가 발생하면 그 피드백을 받아들여 스스로 코드를 수정(Self-correction)하는 루프를 돕습니다.

### 계약-우선 개발 (Contract-First)

백엔드와 프론트엔드가 분리된 환경에서 AI가 API를 수정할 때 타입 드리프트(Type Drift)가 발생하기 쉽습니다. oRPC, tRPC, OpenAPI, Protobuf 등을 활용해 <strong>계약-우선(Contract-First)</strong> 방식으로 개발하면, AI가 백엔드 API를 수정할 때 프론트엔드의 타입 에러가 즉시 발생하여 코드 동기화를 강제할 수 있습니다.

### 단일 스키마 흐름

가장 이상적인 구조는 하나의 진실의 원천(Source of Truth)에서 전체 스택의 타입이 파생되는 <strong>단일 스키마 흐름(Single Schema Flow)</strong>입니다.

```text
Zod Schema → Drizzle Table → API Response Type → Frontend Form Validation
     │              │               │                    │
     └──── 하나의 소스에서 전체 스택의 타입이 파생 ────┘
```

이 구조에서는 AI가 베이스 스키마 하나만 읽어도 데이터베이스부터 프론트엔드 폼 검증까지 전체 데이터 흐름을 완벽하게 이해할 수 있습니다. 계층 간 타입 불일치가 구조적으로 발생할 수 없게 됩니다.

> **💡 핵심 요약**: 강력하게 결합된 타입 시스템은 AI의 창의성(할루시네이션)이 버그로 이어지지 않도록 막아주는 튼튼한 울타리 역할을 합니다.

## 3. 보안 가드레일 — AI 생성 코드의 신뢰 경계

AI는 "기능이 동작하는 코드"를 짜는 데는 최적화되어 있지만, "안전한 코드"를 보장하도록 설계되지 않았습니다.

### AI 생성 코드의 보안 현실

여러 보안 연구에 따르면 AI가 생성한 코드의 약 45%가 크고 작은 보안 취약점을 포함하고 있습니다. SQL 인젝션, XSS(크로스 사이트 스크립팅), 안전하지 않은 인증 메커니즘, 커맨드 인젝션 등이 대표적입니다. AI는 코드의 문맥을 패턴으로 이해할 뿐, 그 코드가 실제 운영 환경에서 어떻게 악용될 수 있는지는 고려하지 않습니다.

### "Verify Before Merge" 원칙

AI가 작성한 코드는 본질적으로 <strong>'신뢰할 수 없는 외부 입력'</strong>으로 취급해야 합니다.
- 결제 로직이나 인증 체계 등 보안 크리티컬 영역은 반드시 시니어 엔지니어의 수동 리뷰를 거쳐야 합니다.
- CI/CD 파이프라인에 <strong>SAST/SCA(정적 분석 및 소프트웨어 구성 분석)</strong> 도구를 기본적으로 통합하여 사람의 눈을 통과한 취약점도 시스템이 한 번 더 걸러내야 합니다.

### 구체적 보안 프롬프팅

AI에게 코드를 요청할 때 프롬프트의 구체성이 보안 품질을 결정합니다.

- ❌ **나쁜 예**: "로그인 기능 추가해줘" (가장 취약한 형태의 튜토리얼 코드를 생성할 확률 높음)
- ✅ **좋은 예**: "bcrypt를 활용한 패스워드 해싱, 파라미터화된 쿼리 사용, JWT 인증을 구현하고 시크릿 값은 환경 변수에서 안전하게 주입받도록 구성해줘"

### Dependency Hallucination(슬롭스쿼팅) 방어

AI가 존재하지 않는 가짜 라이브러리를 해결책으로 제시하는 <strong>의존성 환각(Dependency Hallucination)</strong> 현상이 종종 발생합니다. 공격자들은 AI가 자주 지어내는 가짜 패키지 이름을 미리 선점하여 악성 코드를 심어두는 '슬롭스쿼팅' 공격을 시도합니다.
이를 방어하기 위해서는 `pnpm`과 같이 엄격한 의존성 관리를 강제하는 패키지 매니저를 사용하고, AI가 새로운 의존성을 추가할 때 알려진 레지스트리(npm, PyPI)와 교차 검증하는 과정이 필요합니다.

### 환경 변수 격리와 크리덴셜 관리

AI 에이전트가 로컬 환경에서 도구를 사용할 때 프로덕션 크리덴셜에 접근하지 못하도록 철저히 격리해야 합니다. 코드베이스에는 `.env.example`만 노출하고, 실제 시크릿은 Vault나 클라우드 Secret Manager를 통해 실행 타임에 주입되도록 설계하여 보안 사고를 원천 차단해야 합니다.

> **💡 핵심 요약**: AI 에이전트는 타자를 무한히 빨리 치는 주니어 개발자와 같습니다. 코드를 짜는 속도보다 그 코드를 검증하고 안전하게 배포하는 시스템의 수준이 더 중요합니다.

## 4. 마무리 — AI 시대 개발자의 역할 변화

"물이 들어오면 수위가 올라갑니다." 누구나 AI의 도움을 받아 쉽게 코드를 작성하고 배포할 수 있는 시대가 되었습니다. 하지만 **유지보수가 가능하고, 확장 가능하며, 안전한 '건강한 시스템'을 배포할 수 있는 사람은 여전히 적습니다.**

개발자의 주된 역할은 '코드 작성자(Code Writer)'에서 <strong>'시스템 설계자이자 AI 오케스트레이터(System Designer & AI Orchestrator)'</strong>로 변화하고 있습니다. 아키텍처적 판단, 보안에 대한 통찰, 성능 튜닝, 그리고 프로젝트의 컨텍스트를 명확히 관리하는 능력이 그 어느 때보다 중요해졌습니다.

| 구분 | 과거의 풀스택 | AI 시대의 풀스택 |
|---|---|---|
| **데이터 계층** | 커스텀 쿼리, 복잡한 ORM 매핑 | 표준 SQL, <strong>스키마-퍼스트(Schema-First)</strong> 설계 |
| **프로젝트 구조** | 자유로운 폴더 구조, 멀티 레포 | <strong>컨벤션(Convention)</strong> 기반 프레임워크, 모노레포 |
| **컨텍스트 관리** | 사람을 위한 README, 구전 지식 | 기계를 위한 AGENTS.md, 시스템 프롬프트, <strong>MCP(Model Context Protocol)</strong> |
| **보안 및 검증** | 구현 후 보안 테스트 (선택적) | Verify Before Merge, 구체적인 보안 프롬프팅 |

이 시리즈를 통해 AI와 함께 성장하고 협업하는 더 나은 코드베이스를 설계하는 데 도움이 되길 바랍니다.
